# CGSim Testing Example

A complete example configuration for running a synthetic grid-computing simulation with [CGSim](https://github.com/REDWOOD24/CGSim).

This example includes:

- a generated 30-site grid topology;
- fully connected, synthetic network links;
- a C++ dispatcher plugin;
- a configurable synthetic workload; and
- SQLite output for simulation events and results.

## Directory structure

```text
testing_example/
├── config/
│   ├── links.json
│   ├── site_topology.json
│   └── test_config.json
├── output/
├── scripts/
│   ├── generate.py
│   └── generate_connections.py
└── testing-plugin/
    ├── CMakeModules/
    ├── include/
    ├── src/
    └── CMakeLists.txt
```

| Path | Purpose |
| --- | --- |
| `config/site_topology.json` | Describes the simulated sites, CPU clusters, disks, and files. |
| `config/links.json` | Describes network bandwidth and latency between sites. |
| `config/test_config.json` | Main CGSim configuration for the example. |
| `scripts/generate.py` | Recreates the synthetic site topology with a fixed random seed. |
| `scripts/generate_connections.py` | Recreates the site-to-site network links with a fixed random seed. |
| `testing-plugin/` | C++ shared-library plugin implementing workload generation, dispatching, and output hooks. |
| `output/` | Default destination for the generated SQLite database. |

## Prerequisites

Build and install CGSim before using this example. The project currently expects:

- a C++17 compiler;
- CMake 3.12 or newer;
- SimGrid;
- Boost;
- SQLite3; and
- an installed CGSim development package discoverable by CMake.

See the repository-level documentation for the versions and installation procedure used by CGSim.

## Quick start

### 1. Clone and build CGSim

```bash
git clone --branch latest_changes https://github.com/REDWOOD24/CGSim.git
cd CGSim

cmake -S . -B build
cmake --build build --parallel
sudo cmake --install build
```

Depending on your installation prefix, you may need to set `CMAKE_PREFIX_PATH`, `LD_LIBRARY_PATH`, or `DYLD_LIBRARY_PATH`.

### 2. Build the testing plugin

From the repository root:

```bash
cmake -S testing_example/testing-plugin \
      -B testing_example/testing-plugin/build

cmake --build testing_example/testing-plugin/build --parallel
```

The build creates a shared library named similar to:

- macOS: `libTestingPlugin.dylib`
- Linux: `libTestingPlugin.so`
- Windows: `TestingPlugin.dll`

If CMake cannot locate an installed dependency, provide its installation prefix:

```bash
cmake -S testing_example/testing-plugin \
      -B testing_example/testing-plugin/build \
      -DCMAKE_PREFIX_PATH="/path/to/install/prefix"
```

### 3. Update the configuration paths

`config/test_config.json` contains machine-specific absolute paths. Replace them with paths valid on your system.

At minimum, update:

- `Sites_Information`;
- `Sites_Connection_Information`;
- `Dispatcher_Plugin`; and
- `Custom_Parameters.output_file`.

Example:

```json
{
  "Grid_Name": "ATLAS-GRID",
  "Sites_Information": "/absolute/path/to/CGSim/testing_example/config/site_topology.json",
  "Sites_Connection_Information": "/absolute/path/to/CGSim/testing_example/config/links.json",
  "Dispatcher_Plugin": "/absolute/path/to/CGSim/testing_example/testing-plugin/build/libTestingPlugin.so",
  "Limited_Sites": [],
  "Custom_Parameters": {
    "Num_of_Jobs": "1000",
    "output_file": "/absolute/path/to/CGSim/testing_example/output/testing.db"
  }
}
```

Use the platform-appropriate plugin filename shown in the previous section.

Ensure the output directory exists:

```bash
mkdir -p testing_example/output
```

### 4. Run the simulation

Run CGSim with the example configuration:

```bash
cg-sim -c testing_example/config/test_config.json
```

When using the executable directly from the repository build directory:

```bash
./build/cg-sim -c testing_example/config/test_config.json
```

The exact executable location can vary with the selected CMake generator and installation layout.

## Configuration

### Main configuration

`config/test_config.json` defines the simulation inputs and plugin settings.

| Field | Description |
| --- | --- |
| `Grid_Name` | Human-readable name of the simulated grid. |
| `Sites_Information` | Path to the site-topology JSON file. |
| `Sites_Connection_Information` | Path to the network-link JSON file. |
| `Dispatcher_Plugin` | Path to the compiled testing plugin. |
| `Limited_Sites` | Optional subset of sites to include. An empty array uses all configured sites. |
| `Custom_Parameters.Num_of_Jobs` | Number of jobs generated by the testing workload. |
| `Custom_Parameters.output_file` | SQLite database written by the plugin. |

Values under `Custom_Parameters` are represented as strings in the current example.

### Generated topology

`scripts/generate.py` creates a deterministic synthetic topology containing:

- 30 sites named `Site0` through `Site29`;
- 1,000 files per site;
- 30,000 globally unique file IDs;
- between 1 and 4 CPU clusters per site;
- between 100 and 2,000 CPU units per cluster; and
- disk definitions for `CALIBDISK`, `DATADISK`, `LOCALGROUPDISK`, and `SCRATCHDISK`.

A fixed random seed is used, so rerunning the script produces repeatable data.

### Generated network links

`scripts/generate_connections.py` creates one link for every unique pair of the 30 sites. Each link receives synthetic:

- bandwidth between approximately 25,000 and 35,000 Mbps; and
- latency between 1 and 50 ms.

The script also uses a fixed random seed.

## Regenerating the input data

The generator scripts write their output to the current working directory. Run them from `testing_example/config` so they replace the expected files:

```bash
cd testing_example/config

python3 ../scripts/generate.py
python3 ../scripts/generate_connections.py
```

The scripts overwrite `site_topology.json` and `links.json`.

Because the generators are deterministic, regenerated files should remain stable unless the scripts or their seeds are changed.

## Testing plugin

The plugin is built as a shared C++ library named `TestingPlugin`. It implements the CGSim `DispatcherPlugin` interface and delegates responsibilities to three components:

- `WORKLOAD_MANAGER` creates the workload;
- `DISPATCHER` assigns jobs to resources; and
- `OUTPUT` records simulation lifecycle, execution, transfer, read, and write events.

The plugin exports the factory function expected by CGSim:

```cpp
extern "C" TestingPlugin* createTestingPlugin();
```

Its CMake project links against SimGrid, Boost, CGSim, and SQLite3.

## Output

By default, the example is configured to write:

```text
testing_example/output/testing.db
```

The file is a SQLite database populated by the testing plugin. You can inspect it with the SQLite command-line client:

```bash
sqlite3 testing_example/output/testing.db
```

Useful SQLite commands include:

```sql
.tables
.schema
.quit
```

Delete or rename an existing database before a clean run when you do not want results from separate simulations to share the same file.

## Customizing the example

### Change the workload size

Edit `Num_of_Jobs` in `config/test_config.json`:

```json
"Num_of_Jobs": "100"
```

A smaller value is useful for smoke tests; larger values exercise the simulation more heavily.

### Limit the simulation to selected sites

Set `Limited_Sites` to site names from the topology:

```json
"Limited_Sites": ["Site0", "Site1", "Site2"]
```

Leave it empty to make all configured sites available:

```json
"Limited_Sites": []
```

### Change topology characteristics

Edit `scripts/generate.py` to adjust the number of sites, files, CPU clusters, CPU capacity, disk bandwidth, or storage capacity, then regenerate the topology and links.

Keep the topology and connection generators consistent. For example, changing the number or naming of sites in one script requires the same change in the other.

## Troubleshooting

### CGSim cannot load the plugin

Check that:

- `Dispatcher_Plugin` is an absolute path;
- the shared library exists at that path;
- the filename extension matches your operating system;
- CGSim and the plugin were built for compatible architectures; and
- all runtime libraries are discoverable.

On Linux, inspect dependencies with:

```bash
ldd testing_example/testing-plugin/build/libTestingPlugin.so
```

On macOS:

```bash
otool -L testing_example/testing-plugin/build/libTestingPlugin.dylib
```

### CMake cannot find CGSim or SimGrid

Pass the relevant installation prefix through `CMAKE_PREFIX_PATH`:

```bash
cmake -S testing_example/testing-plugin \
      -B testing_example/testing-plugin/build \
      -DCMAKE_PREFIX_PATH="/path/to/cgsim;/path/to/simgrid"
```

You may also need to set package-specific directory variables according to your local installations.

### Configuration files cannot be opened

The checked-in `test_config.json` uses absolute paths from the original author's machine. Replace every path before running the example.

### No database is created

Confirm that:

- the parent output directory exists;
- `Custom_Parameters.output_file` points to a writable location;
- SQLite3 was found when the plugin was built; and
- the simulation reaches the plugin's output hooks without an earlier configuration or loading error.

## Reproducibility

Both data-generation scripts initialize their own fixed random seeds. This makes the generated topology and network parameters reproducible and suitable for repeatable testing.

Simulation results may still vary if runtime behavior, dependency versions, dispatch logic, or CGSim internals change.
